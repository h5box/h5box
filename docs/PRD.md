# H5Box PRD（基于当前代码反推）

## 1. 文档信息

- 产品名称：H5Box
- 当前定位：网页小程序启动器 / 浏览器内桌面环境
- 文档版本：V0.1
- 文档性质：反向 PRD（根据现有实现、README 与代码结构整理）
- 适用范围：h5box 项目当前已实现能力 + 近期可延展方向

## 2. 产品概述

H5Box 是一个运行在浏览器中的本地化 H5 应用容器。用户可以将 HTML5 应用以 ZIP 包形式安装到浏览器本地，在类似桌面的界面中进行管理、打开、重命名、导出、备份与卸载。

除本地 ZIP 安装外，H5Box 还支持将在线网页包装成“网页小程序”安装到本地，并提供一套面向应用市场或第三方应用的系统桥接 API，使应用可以在授权后调用宿主能力，例如安装应用、读取已安装应用、打开其他应用等。

一句话定义：

> H5Box 旨在成为一个无需原生安装、可离线持久化、面向个人与开发者的浏览器应用桌面。

## 3. 背景与问题

### 3.1 用户当前痛点

- 普通网页入口分散，缺少统一的“桌面式”管理体验。
- HTML5 小应用难以像桌面 App 一样被安装、整理、备份和再次打开。
- 本地收集的 H5 工具、演示页、小游戏、内部页面缺少轻量运行容器。
- 第三方应用市场或聚合页即使能展示应用，也缺乏标准化的“安装到本地”机制。

### 3.2 产品机会

- 借助浏览器、IndexedDB 与 PWA，可以低成本提供近似“桌面系统”的体验。
- 用 ZIP 作为应用分发载体，天然适合本地保存、导入导出与离线运行。
- 通过标准化 bridge API，可以形成“应用市场 / 应用容器 / 应用包”的生态闭环。

## 4. 产品目标

### 4.1 核心目标

- 让用户可在浏览器内安装、运行和管理 H5 应用。
- 提供足够轻量但完整的“桌面式”应用管理体验。
- 保障本地持久化、离线可用和数据可备份恢复。
- 为第三方市场或应用提供可授权的系统 API，提升生态扩展能力。

### 4.2 非目标

- 不提供账号体系、云端同步、多端实时同步。
- 不承担复杂应用审核平台职责。
- 不追求原生级系统权限或原生 OS 集成能力。
- 不以内置内容社区作为当前阶段核心。

## 5. 目标用户

### 5.1 核心用户

- H5 工具重度用户：希望把常用网页工具整理成“桌面应用”。
- 独立开发者：需要一个低门槛容器分发和测试自己的 HTML5 应用。
- 内部团队 / 个人效率用户：想把内部页面、轻应用、本地工具封装成可重复使用入口。

### 5.2 次级用户

- 应用市场开发者：基于桥接接口开发“应用市场”类应用。
- 演示 / 教学用户：将网页 Demo、实验项目、本地作品作为独立应用管理。

## 6. 产品定位与价值主张

### 6.1 产品定位

H5Box 不是传统浏览器书签页，也不是操作系统级桌面替代品，而是一个“浏览器内的轻桌面 + H5 应用容器”。

### 6.2 核心价值

- 可安装：网页或 ZIP 应用可以被显式安装，而不是仅作为链接收藏。
- 可管理：支持图标、名称、顺序、元信息、导出、卸载。
- 可运行：支持内部窗口或浏览器弹窗两种运行模式。
- 可恢复：支持整机级备份 ZIP 与批量恢复。
- 可扩展：通过 bridge API 与权限机制支持生态化接入。

## 7. 主要使用场景

### 场景 A：安装本地 ZIP 应用

用户将包含 index.html 的 ZIP 拖入桌面，系统自动解析应用元数据并安装到本地，随后在桌面生成应用图标。

### 场景 B：把网页封装成小程序

用户输入网页标题与 URL，系统自动生成包装 ZIP，将在线网页作为应用安装到桌面，并在可内嵌时用 iframe 打开，无法内嵌时自动回退外部窗口。

### 场景 C：从应用市场安装

用户先安装“应用市场”应用，再通过市场调用宿主 bridge API，经用户授权后完成应用安装与打开。

### 场景 D：像桌面一样运行应用

用户点击应用图标，应用以内部窗口或弹窗方式运行，窗口支持拖拽、缩放、最大化与关闭。

### 场景 E：备份与恢复

用户在系统设置中一键导出所有应用为 ZIP 备份包；之后重新导入该 ZIP，即可恢复应用及大部分元信息。

## 8. 核心流程

### 8.1 安装流程

1. 用户选择安装入口：拖拽 ZIP / 文件选择 / 推荐应用 / 在线网页封装。
2. 系统解析 ZIP，读取 index.html 及元信息。
3. 系统识别标题、描述、作者、版本、包名、图标、官网等字段。
4. 若检测到相同文件哈希，则跳过重复安装。
5. 若检测到相同 ppIdentifier 的旧版本，则提示用户是否更新。
6. 安装完成后写入 IndexedDB，并在桌面展示新应用。

### 8.2 运行流程

1. 用户点击图标。
2. 系统根据设置决定内部窗口打开或弹窗打开。
3. 若为内部窗口，加载应用 iframe，并恢复窗口状态。
4. 若应用调用 bridge API，系统执行权限校验 / 授权弹窗 / 请求处理。

### 8.3 备份恢复流程

1. 用户导出全部应用。
2. 系统生成 pps.json + pps/*.zip 的压缩包。
3. 用户重新导入该 ZIP 时，系统识别其为备份包而非单应用包。
4. 系统逐个恢复应用包及元数据。

## 9. 功能需求

### 9.1 桌面与应用入口

**目标**：提供统一的应用承载界面。

**需求点**：

- 以桌面网格展示已安装应用。
- 支持应用图标拖拽排序，并持久化排序结果。
- 新安装应用应显示“新应用”视觉提示，首次打开后取消提示。
- 桌面空白处支持右键菜单。
- 桌面需展示系统版本与 DB 版本。

### 9.2 应用安装

**目标**：降低应用接入门槛。

**需求点**：

- 支持拖拽 ZIP 到桌面安装。
- 支持文件选择安装 ZIP。
- ZIP 至少需包含根目录或单层目录下的 index.html。
- 支持从 URL 下载 ZIP 后安装。
- 支持推荐应用一键安装。
- 支持用户输入网页 URL，将在线网页封装为本地应用安装。
- 安装时显示状态与进度，如“解析中 / 下载中 / 安装中 / 完成”。
- 安装失败时需给出清晰错误提示。

### 9.3 元数据解析与生成

**目标**：尽量自动完成应用信息识别。

**需求点**：

- 从 	itle、meta[name=description]、uthor、keywords、ersion 中解析应用元数据。
- 从 meta[name=app-identifier] 获取应用唯一包名。
- 若缺少 ppIdentifier，系统需自动生成稳定标识。
- 从 link[rel=icon] 解析图标；若找不到则自动生成默认图标。
- 从 link[rel=canonical] 提取官网地址。

### 9.4 应用管理

**目标**：让安装后的应用可以持续维护。

**需求点**：

- 支持打开应用。
- 支持新窗口打开应用。
- 支持重命名应用。
- 支持编辑应用信息，包括名称、图标、描述、作者、包名、官网、仓库地址。
- 支持导出单个应用 ZIP。
- 支持卸载应用。
- 若应用存在仓库地址，支持一键打开开源地址。
- 应用图标悬浮时展示信息卡片，包括作者、描述、安装时间、关键词与包体积。

### 9.5 应用运行容器

**目标**：提供接近桌面系统的运行体验。

**需求点**：

- 支持内部窗口模式运行应用。
- 支持弹窗模式运行应用。
- 内部窗口支持拖拽、调整大小、聚焦置顶、最大化、关闭。
- 窗口位置和尺寸需本地持久化。
- 用户可在设置中切换默认打开方式。
- 在线网页封装应用在 iframe 被拒绝时，系统需自动回退到外部窗口打开。

### 9.6 备份、恢复与迁移

**目标**：保证用户资产可迁移。

**需求点**：

- 支持导出全部应用为单个 ZIP 备份包。
- 备份包应包含 pps.json 清单与每个应用的 ZIP 原文件。
- 导入 ZIP 时，系统应自动识别是否为“全量备份包”。
- 识别为备份包后，系统应恢复应用包、标题、描述、作者、版本、关键词、图标、官网、仓库地址、排序等信息。
- 提供“清空全部应用”能力，但需双重确认与倒计时防误触。

### 9.7 权限与系统桥接 API

**目标**：在安全前提下开放宿主能力。

**需求点**：

- 应用通过 postMessage 与宿主通信。
- 敏感操作必须先申请权限。
- 权限授权结果需按应用维度持久化。
- 当前支持的权限包括：
  - system.installApp
  - system.uninstallApp
  - system.getInstalledApps
  - system.openApp
  - system.readAppSource
- 当前支持的系统 API 包括：
  - system.requestPermissions
  - system.installApp
  - system.getInstalledApps
  - system.uninstallApp
  - system.openApp
  - system.getAppSource
- 当应用运行在弹窗中时，权限申请应支持弹窗式授权页。

### 9.8 系统设置与个性化

**目标**：提供基础系统级偏好配置。

**需求点**：

- 支持浅色 / 深色 / 跟随系统三种主题模式。
- 支持默认打开方式切换：内部窗口 / 弹窗。
- 支持查看当前存储空间占用估算。
- 支持进入备份与清空系统数据流程。

## 11. 非功能需求

### 11.1 可用性

- 核心操作应支持零学习成本：拖拽安装、点击打开、右键管理。
- 错误提示应尽量说明原因，例如 ZIP 非法、缺少 index.html、权限被拒绝等。

### 11.2 性能

- 桌面打开后应快速加载已安装应用列表。
- 常规应用安装应在可接受时间内完成，并显示安装进度。
- 多窗口情况下应保证基本交互流畅。

### 11.3 可靠性

- 刷新页面后，已安装应用、排序、权限与窗口状态不应丢失。
- 备份包应可在同类环境中恢复。

### 11.4 安全性

- bridge API 必须经过显式授权。
- 权限粒度应按能力拆分，而不是一次性授予全部系统能力。
- 对第三方网页封装应用，应接受其可能无法 iframe 内嵌的现实约束并提供回退方案。

## 12. 当前版本成功指标（建议）

### 12.1 产品指标

- 成功安装率
- 首次安装完成时间
- 应用打开成功率
- 备份成功率与恢复成功率
- 用户每周打开应用次数
- 已安装应用数中位数

### 12.2 生态指标

- 通过 bridge API 完成安装的应用数
- 使用权限系统的第三方应用数
- 应用市场安装转化率

## 13. 当前已识别限制

- 当前数据主要保存在单浏览器本地，不具备天然跨设备同步能力。
- 在线网页封装受目标站点 iframe 策略影响。
- 权限机制已具备基础能力，但尚未见到更细粒度的审计、撤销入口与风险分级设计。
- 目前产品更偏桌面端体验，移动端虽可使用，但不是最优交互主场。

## 14. 建议的阶段规划

### P0：现有能力固化

- 完善安装、打开、编辑、卸载、备份、恢复主路径。
- 打磨权限申请与错误提示体验。
- 明确产品对外定位与默认入口。

### P1：生态增强

- 完善应用市场接入规范与 SDK。
- 增加权限管理面板、授权记录、撤销授权。
- 增加应用分类、搜索、筛选。

### P2：平台化能力

- 增加云备份 / 云同步。
- 增加应用版本管理与回滚。
- 增加应用评分、推荐、分发后台等生态能力。

## 16. 我对当前项目的总结

如果只根据现有实现来判断，H5Box 当前最像：

> 一个面向桌面浏览器、以本地安装和管理 H5 应用为核心、同时具备初步生态扩展能力的浏览器桌面系统。

它的第一阶段竞争力不在“内容社区”，而在：

- 本地化安装与持久化能力
